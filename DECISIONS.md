# Decisions

Notable calls made while building Tieout, newest last. The team is hands-off, so each decision records why.

1. **Sandbox: plain Docker + gVisor (runsc), not OpenSandbox.** As CLAUDE.md recommends: `--network none` under gVisor gives zero network with the fewest moving parts. Every container: read-only root, `/in` read-only, `/work` and `/out` writable, tmpfs `/tmp`, `--cap-drop=ALL`, `no-new-privileges`, uid 10001, 1 CPU, 1 GiB, 256 pids, 60 s per exec (`timeout -s KILL`), 15 minute TTL.
2. **Flattened sandbox image.** The `python:3.12-slim` base sets `GPG_KEY` (a public key fingerprint, not a secret) and it showed up in the attested environment. The image is built from `scratch` with only the variables we choose, so the "no secrets in environment" check is clean and honest.
3. **tieout_lib does the math, the model does the judgment.** Money is `Decimal`; outputs are byte-identical across runs (fixed xlsx timestamps and zip entry times), which is what makes Replay possible. The agent adapts loaders to each client's export format, investigates leftovers, and writes the memo.
4. **Unidentified items keep the difference at 0.00.** They are listed on the book side as "unidentified items flagged for review" (no AJE), so every cent is either matched, timing, adjusted, or explicitly flagged. Runs with flagged items get status `needs_review` (amber).
5. **The replay sandbox gets the original `run_context.json`.** The workpaper header names the run id; replaying with the original inputs byte for byte (including that file) makes the outputs identical.
6. **Matching window is 5 calendar days.** A 3 business day posting lag over a weekend is 5 calendar days; the generator produces that, so the library handles it.
7. **Model: GLM 5.3 with native tool calls,** GLM 5.3 Flash as automatic fallback, strict JSON action protocol as a second fallback. Measured: a tool call round trip is about 1.5 to 3 s; a full client run is 6 to 8 tool calls, about 35 s alone.
8. **Deployment without SSH.** This build environment cannot open outbound SSH (only HTTPS on 443 through a proxy). Hosts run a small pull-based ops agent that fetches commands from Object Storage through a presigned URL and executes only commands signed with an Ed25519 key held by the operator (the hosts have only the public key, commands carry a monotonic id and an expiry, results return through presigned PUT URLs). No inbound port is opened for operations; a tampered command is rejected (tested).
9. **Public hostname via sslip.io.** No domain is available, so the control plane is reachable as `<ip-with-dashes>.sslip.io` with a Let's Encrypt certificate from Caddy.
10. **Sandbox host keeps a public IPv4 but accepts no inbound traffic.** Its Vultr firewall group has no rules and nftables drops all inbound except the runner port from the control plane's VPC address. Outbound is needed at build time (packages, image pulls). A NAT gateway would remove the public IP; it is a documented next step, not needed for the containment story (sandboxes themselves have no network at all).
11. **Postgres access** goes over the VPC or the public host with `sslmode=require`, with trusted sources limited to the control-plane IP and the VPC subnet.
12. **Commits are authored with the repo owner's GitHub noreply identity** and carry no AI co-author trailer, per CLAUDE.md.
13. **Blocked early on the Vultr account API** (IP access control rejected this environment's egress range). Built and tested everything locally meanwhile (real gVisor, local Postgres, local runner); provisioning is one command once access works.
14. **Blocked by the account's monthly fee limit.** After the IP allowlist was fixed, Vultr refused every new VM and database because the shared account is at its monthly fee limit (the other project uses about $190 of it). Provisioning now creates whatever fits in priority order (control plane, sandbox host with smaller fallbacks, managed database) and retries every 5 minutes; deploy adapts: split architecture when a sandbox host exists, otherwise an all-in-one host; a local Postgres container when the managed database does not fit.
15. **Public demo safeguards.** The demo credentials are public, so starting a close is limited per IP and per user, only one close runs at a time, and in the public deployment the kill switch auto-resumes after 15 minutes (every use is in the hash-chained audit log). A daily token budget caps spend.
16. **Re-run a single client** inside a close, so one failed client never forces a full re-run on stage; batch views show the newest run per client.
17. **Runner pool.** The control plane can spread runs across several sandbox hosts (`SANDBOX_RUNNER_URLS`); control actions (kill switch, resume, warm-up, health) go to every host. A second host is optional and never blocks the deploy.
18. **Model text follows house style.** Model-written memos, summaries and step notes are normalized to remove em dashes before they are stored and shown.
19. **Narration fallback.** Vultr text-to-speech is the narration engine; while it returns errors for every voice, the video pipeline falls back to a local Piper voice for the affected lines and records which engine voiced each line.
20. **No NetBird.** The bonus has no cash prize (team decision: last priority) and needs a self-hosted management server or an interactive account signup; skipped in favor of demo reliability.
21. **Sandbox host is 4 vCPU / 8 GB, not 8 / 16.** When the fee limit eased, the 8 vCPU plan still did not fit; provisioning fell back to `vc2-4c-8gb`. A close of 12 clients still finishes in about 54 s on it (12 sandboxes, 1 GiB cap each, real usage about 200 MB).
22. **One sandbox host for the demo.** After the other project freed some capacity, a second sandbox host (`vc2-4c-8gb`, $40/month) was still refused by the account's monthly fee limit. One host passes the 10-run public check (51 to 79 s per close of 12), so the demo keeps one host; the runner pool is ready for a second when the limit allows.
